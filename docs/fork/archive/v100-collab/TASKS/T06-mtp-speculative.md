# T06: MTP 投机解码 (decode 翻倍的唯一路线)

状态: SKIPPED (用户决定 2026-09-22; 生产已用 MTP3)
优先级: P1
预期收益: 有效 tg128 26.64 -> 40+ (kernel 侧上限只有 33-35, 硬墙 40.9)

## 背景

- decode 是带宽墙: 权重 21.97GB/token, 100% 带宽也只有 40.9 t/s
- 本模型的 GGUF 自带 MTP head (`blk.64`, `nextn.*` 张量), 投机解码可以"一次读权重出多 token",
  有效吞吐 = 基础吞吐 x 接受率收益, 是超过 41 的唯一途径
- 报告已知: 服务端 8k prompt 含 MTP 的 prefill 从 861 掉到 800 (-7%), 但没测 MTP 的 tg

## 方法

1. 基线: `tg128` 在 MTP 关闭 / 开启下的数字, 接受率 (acceptance rate), 每步平均接受 token 数
2. 调参: draft 长度/最小长度 (llama.cpp 侧对应参数), 找到本模型最优; 注意 V100 上 MTP 前向也要读一遍 MTP 权重 (blk.64 很小, 可忽略)
3. 服务端配置: prefill 阶段禁用 MTP (避免 -7%), 生成阶段启用; 确认切换无副作用
4. 与 T05 联动: 若 T05 把基础 tg 提到 30+, MTP 的绝对收益按比例放大

## 验收

- 生成阶段有效 tg128 >= 40 (目标), 若接受率低导致达不到, 给出实测接受率与理论上限
- prefill 不因 MTP 退化 (pp512/pp4096 与 T04 配置一致)
- PPL/输出质量: 投机解码必须与不投机解码输出分布一致 (采样参数一致时), 记录对比方式

## 注意

- 这是"有效吞吐"提升, 不是物理带宽提升; 报告中要分开写"带宽效率"和"有效 tok/s", 避免和 T05 的数字混在一起

## Analyst 说明 (2026-09-22): 已提前到队列第 3 位

- T05 已证明纯 kernel 路线最多 +8% (26.6 -> 28.5-30), **decode 的有效翻倍只有 T06 这一条路**, 所以提前做
- 方法补充: llama-bench 不支持 MTP, 用 llama-server 对比 (同一 prompt, 生成阶段 on/off):
  - 记录: 生成 tg、acceptance rate、每步接受 token 数、prefill t/s (MTP on/off)
  - prefill 阶段按已有实测关 MTP (861 vs 800, -7%)
- 验收保持: 生成阶段有效 tg >= 40; prefill 不退化; 若接受率不足, 给出实测接受率与理论上限
- 若接受率低于预期 (比如 < 1.5 token/步), 仍要如实报告: 这决定了是否需要看其他投机方案 (小的 draft 模型)
