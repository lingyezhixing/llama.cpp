# MTP"降智"问题的完整阐述

> 2026-09-26。本文是对整个问题的完整推理与定性，综合了封存（2026-09-23）的实测、
> T24 的状态轴实现、以及双方对"正确性"的讨论。配套实现见 `05-T24-ReplaySSM/`，
> 选核轴实测见 `04-T20源码排查/`。

---

## 0. 问题陈述

现象：Qwen3.8-27B（V100）开启 MTP（投机解码）后，用户反馈"明显降智"。
特征：

- 不是每次都出现，也不是稳定复现；一旦出现往往是"换了一篇文章"式的整体偏移；
- 在极端问题、小众领域更明显，普通任务上"也能感觉到一点但说不上来"；
- 单次对比下，开 MTP 与大 model 不开 MTP 的输出无法逐位一致。

需要回答三个问题：

1. 这算不算 bug？是谁的 bug？
2. 哪条路径是"正确"的？上游 no-MTP 就是基准吗？
3. 能修吗？修什么、代价是什么？

---

## 1. 第一性原理：浮点世界没有"唯一正确解"

### 1.1 结合律不成立

IEEE 754 只规定**每一次**加减乘除的舍入，**不规定归约（求和）顺序**；
而浮点加法不满足结合律：`(a+b)+c != a+(b+c)`。

于是任何一次归约都在"选一个合法顺序"：attention 的 online softmax、GDN 的递推、
matmul 的 split-K、KV 切分后的合并……全都是。

### 1.2 顺序由什么决定

| 因素 | 例子 |
|---|---|
| kernel 实现 | FA 的 VEC / TILE / MMA 三种核 |
| 数据布局 | GDN 的 vec4 布局 vs 标量布局（lane→行的映射不同） |
| 切分策略 | FA 的 split-K 段数 pb、matmul 的 split-K、张量并行 |
| 编译 | FMA 收缩、快速数学函数 |
| 硬件/驱动/库版本 | 不同卡、不同 CUDA、不同 kernel 版本 |
| **批形状** | 单 token decode vs 2~4 token verify/prefill |

### 1.3 所以：没有绝对基准

- 上游 no-MTP 只是**一个约定**——换一张卡、换驱动、换 batch size、换 llama.cpp 版本，
  它自己也漂；
- 模型**训练时**的前向又是另一套算术（bf16 matmul、训练版 FA、不同的切分），
  推理误差与训练误差**不同分布**；
- 只有在**实数精确算术**下，"正确"才是唯一且可定义的——但那不可达。
  fp64 只是把误差压到使近并列概率趋零，从而 argmax 确定化；它既不等于训练数值，
  也不等于任何生产路径。

**结论：我们连"定义正确"的能力都没有。** 能定义的只有**不变量**（见 §5）。

## 2. 三层误差源：量级与性质都不同

| 层 | 来源 | 性质 | 量级 | 我们的处理 |
|---|---|---|---|---|
| **量化** | 权重 / 激活 / KV 量化 | **系统性偏置**（改变的是模型函数本身） | ~1e-3 及以上 | PPL / benchmark 门禁接受 |
| **底噪** | 训练≠推理的算术、跨引擎/版本/显卡、同类算子在不同批形状下的顺序差 | 零均值漂移 | ~1e-6 | 不可消除，只能文档化 |
| **MTP 特有** | verify 批（2~4 token）与 decode 批（1 token）的算子选型/布局差 | 零均值漂移，同量级，**同环境内可对比** | ~1e-6 | 分两条轴修（状态轴 / 选核轴） |

两个必须澄清的点：

1. **MTP 并没有"额外引入一类误差"**。它的误差与底噪同量级、同样源于结合律；
   它真正的特殊性是**制造了同环境 on/off 对照**，把这个天然的误差类暴露出来了。
   不开 MTP 时没有对照，所以同样的漂移难以被发现。
2. **量化不能和上面两层混为一谈**。量化不是零均值噪声，而是**系统性偏置**：
   量级大三个数量级，会改写长尾 token 概率、改变 top-k 集合，**可以系统性地**改变行为
   （这就是它必须用 PPL/benchmark 门禁、而不能靠"路径一致"来修的原因）。

正确的叠加图景：

```
量化（系统性、大、被 PPL 门禁接受）
  └── 训练/推理数值差（零均值底噪、无法定义基准）
        └── MTP verify/decode 批型差（同量级、同环境可对比 → 唯一"能修且用户能观察"的轴）
```

## 3. 翻转机制：从 1e-6 到"另一篇文章"

### 3.1 放大链条

```
末位差(~1e-6)
  -> 沿网络被 Jacobian 放大（可达 1e-4 ~ 1e-2）
  -> 在某步 top1/top2 的 gap 小于"当前累积扰动"处，采样/argmax 翻转
  -> 自回归把这一次翻转放大成整条轨迹不同
```

要点：**翻转阈值不是固定的 1e-6，而是"当时的累积扰动"**。
封存实测的 d0@207 翻转对应的 top1/top2 gap 是 0.068 nats——远大于 1e-6，
正是累积放大后的结果。

### 3.2 四个"不一定"

1. 翻转了**不一定**输出不同 token（gap 相对扰动仍够大时，换序不换人）；
2. 换了 token **不一定**改变后续轨迹（后续可能回归到同一路径）；
3. 改了轨迹**不一定**变差——**两条轨迹都是模型的合法采样**；
4. 单次变差**不构成**系统性降智的证据。

## 4. 期望无偏 vs 单次方差：社群"降智"观感的真实来源

### 4.1 期望层面

扰动零均值 ⇒ 在**大样本聚合指标**上，开/关 MTP 的表现应当一致
（实测：PPL 两边都是 4.3567；封存：修复前后 PPL 不变）。

### 4.2 方差层面（关键）

但翻转的**发生概率**和**后果**是任务相关的：

- **高度训练过的内容**：logit margin 大、近并列少 ⇒ 几乎不翻 ⇒ 轨迹稳定、有"回归性"；
- **小众 / 训练不足 / 极端问题**：模型本来就在"窄脊"上、margin 小 ⇒ 任何扰动都翻；
  且长链推理会把一次错翻放大成整段崩。

所以社群说的"降智"本质是：**方差在难任务上被放大，而不是均值下移**。

要证明"系统性降智"必须用多 prompt、多样本的聚合指标；单次对比看不出。
同时要承认：对"模型勉强能做"的题，方差放大在实践中就是伤害——
用户看到的是单条轨迹的成功率下降，这个感受是真实的，只是它不是"模型退化"。

### 4.3 与量化的叠加

量化已经改变了模型函数（系统性偏置，尤其在长尾），它使模型本身更靠近"窄脊"；
MTP 的顺序漂移再叠加在这个更脆弱的基础上 ⇒ 用户感知到的"开 MTP 就降智"更明显。
这也是为什么把两件事混在一起讨论时会失焦。

## 5. "正确"的定义：从比特到不变量

### 5.1 不可承诺

- 跨构建 / 跨硬件 / 跨批形状的逐位一致；
- "唯一正确的生成轨迹"。

### 5.2 可承诺（工程不变量）

| 不变量 | 含义 | 现状 |
|---|---|---|
| 同配置确定性 | 同构建 + 同批形状 + 同参数 ⇒ 同输出 | 有 |
| **同构建 batch-invariance** | 同一构建内，开不开 MTP **逐 token 一致** | 分两轴修，见 §6 |
| 分布等价 | PPL / benchmark 不退化（量化的系统性偏差在这一层被门禁） | 有（PPL 4.3567 两边一致） |
| 跨环境差异 | 文档化，不承诺 | 本文 |

### 5.3 训练侧能做什么（理论上）

训练消不掉结合律；能做的只有**降低对末位差的敏感度**：

- QAT / 训练时使用与部署一致的算子；
- 噪声鲁棒训练（让模型不依赖 razor-thin 的 margin）；
- 目标上拉开 logit margin。

所以"理论上可以训练到不出这类问题"要限定为："可以把翻转概率压到接近零"，
而不是"获得唯一正确的解"。

## 6. 我们这套实现里，具体有哪些源

### 6.1 状态 / 回滚轴（T24，已做到精确）

老实现（上游 + 本 fork）：S 缓存保留 `n_rs_seq+1` 个状态平面，回滚 = 按 `rs_idx`
**选平面**（存状态）。
ReplaySSM：只留 1 个 committed 平面，每 token 存 raw inputs（k/v/g/beta），
回滚 = 从 committed 平面**重放** accepted 前缀（重算，与 verify 主循环共用同一段递推代码）。

这条轴的特殊性：它是一个**语义差异**（选面 vs 重算），因此可以也应该做成**精确无损**：

- 实测：老 MTP vs replay MTP，1000 token 贪心**逐 token 完全相同**；
- 逐位自检（fold vs 上批提交态，全层全批）：**0 mismatch**；
- PPL 不变；VRAM −420 MiB；代价 tg ≈ −1.9%。
- 过程中修掉两个确定性 bug：断链批不该 fold（位置连续性判据）、
  `s_copy` 覆盖破坏 conv 回滚（详见 `05-T24-ReplaySSM/README.md`）。

### 6.2 选核轴（封存 T20，未进主线）

| 编号 | 分叉源 | 修复 | 是否动 no-MTP |
|---|---|---|---|
| S1 | FA 小批选核：decode(n_q=1)=VEC，verify(n_q=2~4)=TILE | `vec_limit 2→16`（小批统一 VEC） | decode 不变；≤8 token 的短 prefill 变 |
| S2 | GDN 布局：decode=标量，prefill/verify=vec4（本 fork prefill 优化引入） | 一律 vec4 | **变**（decode 迁就 prefill） |
| S3 | FA split-K 的 pb 随 padded KV 长度变化（上游固有，跨 256 边界就变） | 小批钉常量 | **变**（两边一起换到常量） |

三者叠加 ⇒ MTP on/off 在近并列处必然漂移。
封存修复后验收："n-max 1/2/3 与不开 spec 在短 900 token / 32k 150 / 128k 100 上逐 token 一致"，
代价 −0.5~0.8%（全来自 S2），PPL 不变。

**但要看清语义**：让 verify 与 decode 走同一套算术，必然至少动一方。
封存选择"decode 搬迁"+"两边一起钉 pb"，所以：

- 修复版 **no-MTP 数值也变**（实测 t20fix vs stock 在 d8192@147 分叉）；
- 且修复版与原版**都不等于**上游——因为本 fork 的 prefill 优化（GDN vec4 prefill、
  FA 切分）早已改了末位数值（证据：T19 生产版 greedy d0@207 与原版分叉）。

### 6.3 已知尾巴

- ~~会话状态存取~~ **已修**（提交 `3eae5cdae`）：状态文件现在同时保存 pinned 平面、
  记录张量与 replay 记账；恢复后首个 batch 用 pending 计数 fold 一次，输出与不中断
  运行逐 token 一致（slot save/restore 测试 16/40/60 三种长度全过）。
  跨模式读取（records 存档 → records 关闭）显式报错，不静默出错。
- ~~多序列~~ **已支持**（提交 `3eae5cdae`）：改为 per-sequence 记账（记录 bank = 序列 id、
  每序列独立的 gen/have_rec/读写半区，半区按序列自己交替）；`-np 2/3/4` 交错与并发混合批、
  `-np 4` save/restore 均 ON == OFF 逐 token，自检 0 mismatch。开关默认仍关。
- 未覆盖矩阵：KDA 模型（无权重）；EAGLE3 / DSpark 与 DFlash 走同一 `need_n_rs_seq` 分支，机制相同但无权重可测。
  DFlash 已实测（Qwen3.6-35B-A3B `qwen35moe` + DFlash Q8 草稿，n-max=6，np=1）：greedy 900 token 与
  生产采样 256 token 均 ON == OFF（draft/accepted 统计也相同）、自检 0 mismatch、省 350 MiB；
  吞吐 3 组交错测量在 ±5% 噪声内，无速度结论。DFlash + np=2/4（顺序交错、并发混合批 + 自检、
  生产采样）全部 ON == OFF，np=2 省 ~700 MiB。

## 7. 三条工程路线与取舍

| 路线 | MTP 透明 | no-MTP 数值 | 代价 | 状态 |
|---|---|---|---|---|
| **A 现状（仅 T24）** | 否（近并列仍翻） | 不变 | 0（反而省 420MB） | 已交付，开关默认关 |
| **B 照搬封存修复** | **是**（验收过） | **变**（≠ 现在生产、≠ 上游） | −0.5~0.8% | 补丁在封存，未移植 |
| **C decode-preserving 对齐** | 可能（S3 有边界残差风险） | **不变** | 未知 | 未做：S1 免费、S2 小改可行、S3 需新机制 |

路线 C 的要点：S1 本来就对 decode 中性；S2 可以只对**小批**退回标量布局
（decode=1、verify≤4 都走标量 ⇒ decode 不变，只损失小批的 vec4 收益），
真正难的是 S3——让 verify 采用"decode 在那个位置的 pb"。
封存当时判断"反过来对齐只能逐 token 验证、没有加速"，但严格说这不是逐 token 验证，
值得作为独立课题验证；风险是 verify 与 4 个位置各自的 pb 未必一致，跨 256 边界
那一档可能仍有残差。

## 8. 结论（可对外的准确表述）

1. **不是 bug，也不是"模型退化"**：开 MTP 引入的误差与固有的浮点底噪同量级、
   同样零均值、路径数学等价；它只是制造了同环境对照而变得可见。
2. **没有绝对基准**：上游 no-MTP 只是一个约定；跨引擎/版本/硬件/批形状的漂移天然存在。
   能承诺的只有不变量（同配置确定性、同构建 batch-invariance、分布等价、跨环境文档化）。
3. **"降智"的真实机制**：末位差沿网络放大，在近并列处翻转，自回归放大成合法但不同的轨迹；
   期望无偏，但**方差在难任务上放大**——用户对难任务的成功率下降感受是真实的。
   单次对比不足以证明系统性降智，必须用聚合指标。
4. **可修的是"同环境可对比"的那条轴**：
   - 状态/回滚轴已做到精确无损（T24：老 == 新逐位，省 420MB，自检 0 mismatch）；
   - 选核轴可以把 MTP 做到完全透明，但代价是 no-MTP 数值一起变（路线 B，
     封存已验证）；若要求 no-MTP 数值不变，则走路线 C（待验证）。
5. **量化是另一件事**：系统性偏置、量级大三个数量级，用 PPL/benchmark 门禁接受，
   不能与浮点顺序漂移混为一谈。
